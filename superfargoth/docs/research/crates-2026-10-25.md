## 1. bevy-react

What it is: TSX components with a React-Native-style bridge; intrinsic `<node>/<button>/<text>/<surface>` map to `bevy_ui` nodes; inline `style` objects (camelCase, no CSS files); typed messages both ways; hot reload keeping state; side crates for SVG, canvas, portals, anchors. JS runs on `deno_core` 0.404 (V8), with `tokio`, `resvg/usvg/tiny-skia`, `kurbo`, `ts-rs` in the tree. Tooling is `npx bevy-react init ui` and `npm run watch`, output `ui/dist/app.js`.

Fit with ours: ui.md fixes retained `bevy_ui` organised like CommonUI, MVVM view-models, CSS via `bevy_flair` layered by mod load order (`@layer`), a Luau surface. bevy-react is a second, competing authoring model: styles are inline JS objects (no cascade layers, so the "later mods override earlier ones" story is lost), behaviour is React state (not our headless widgets and focus stack), and input/focus routing is its own. Modders would face TS/npm/bundler on top of Luau and CSS.

Cost: V8 is a very large native dependency (big binary, long first compile, prebuilt static lib download), plus a JS heap and event loop, in a game that is already render-thread bound (hard-problems H1). It is also a second scripting language to sandbox; our Luau sandbox rules would not cover it.

Verdict: skip. Ideas worth reading only: diffing a view tree into `bevy_ui` entities, and `ts-rs` typed messages. If authors want declarative UI, ui.md already plans `.bsn` scenes (Bevy 0.21) over the view-models. It replaces no `sf_ui*` part.

## 2. bevy_open_vat

What it is: OpenVAT vertex animation textures. Offline, the OpenVAT Blender addon bakes per-frame position/normal offsets to an EXR plus a JSON remap (frame counts, bounds, clip names); the glTF is exported without animation or skin data, with UV2 as lookup. At runtime the vertex shader decodes offsets (frame blending), storage buffers batch many entities into few draws, it works with `StandardMaterial` (shadows, normal maps, motion vectors, prepass), per-entity play/pause/seek/speed/one-shot (`VatClipFinished`), desync by start offset. Tiny deps (bevy, bytemuck, serde, serde_json, thiserror). Rust 1.97.1; WebGPU only on web. No tests, one author.

Where it fits: a tier below our LOD 3 ("evaluate no pose", animation.md): far NPCs, creatures, ambient life (guars, scribs, birds, fish) looping a fixed clip set with no gameplay-driven blending. Zero CPU per entity, no GPU skinning, batches well. It does not fit near actors: no IK, no layered/additive blends, no equipment swaps, no per-bone pose for attachments or root-motion events.

Morrowind and assembly: our characters are assembled from parts (character.md "Assembly at runtime"); VAT freezes one assembled mesh per bake, so each distinct outfit needs its own bake and texture (frames x vertices x RGBA16). Good for creatures (one mesh per species) and a few generic crowd archetypes; poor for hundreds of uniquely equipped NPCs. Our bake would need to sample NIF clips through our pose runtime and write EXR+JSON ourselves (the format is simple; no Blender), or bake on load with a compute pass. Needs a spike on one creature (layout, bounds, memory per LOD).

Verdict: adopt later, scheduled with animation LOD/crowd work, starting with creatures. If the crate lags Bevy, take only the format and shader idea (a few hundred lines). Our anim graph stays for everything near.

## 3. bevy_settings_plus

What it is: an extension of `bevy_settings` (persisted settings files) adding `AdapterCaps` (backend, vendor, ray-query support, DLSS support), platform defaults for `DisplaySettings`/`RenderSettings`/`AccessibilitySettings`, a `CapsAware::clamp_to(caps)` trait clamping your own settings once at startup, and bindings applying settings to the primary window and `SettingsCamera` cameras. Optional `dlss` feature needs the NVIDIA SDK at build time, which clashes with the scrib DLSS plugin split. One commit, published the day before this review (0.0.1 yanked minutes after publish).

GPU tier or benchmark? No. No VRAM, tier, named presets, or benchmark in the README. It only clamps what hardware cannot do (e.g. RT without ray query). Our Low/Medium/High/Ultra (`Quality`, `--quality`) and DLSS auto already exist.

Verdict: skip. A small own heuristic is better and keeps one settings store: read `RenderAdapterInfo` (vendor, device type, name) and wgpu `Features`/limits (ray query for Solari), pick a default preset from a short table keyed by device type (discrete / integrated / CPU) plus a name list, allow a first-run override; add an optional timed test only if wanted. Revisit if it matures and stops owning persistence.

## 4. bevy_grass

What it is: GPU-generated grass. Compute shaders pick the blades near each camera, so nothing is stored per blade and cost is roughly independent of field size (4 km about equal to 200 m). Curved tapered blades, three wind layers, backlighting, colour variation, a far-grass material that continues colour past the last blade, optional flowers/ferns/tufts/bare and dry patches. Casts and receives shadows, fog, writes depth/normal/motion-vector prepasses and the deferred G-buffer. Interaction: `GrassInteractor` (disc), `GrassInteractorFootprint` (box), Rapier/Avian colliders (optional), edits (mow, burn, regrow), CPU `GrassSampler` (stealth, footsteps). 36 hot-reloaded `.grass.ron` presets, `GrassQuality` tiers, per-camera `GrassCamera`. Reported GPU cost at High, 1080p, 4x MSAA, shadows on: 0.26 to 3.4 ms depending on GPU and scene; 512 interactors about 0.02 ms. Light deps (bevy features, bytemuck, ron, serde). Needs compute (no WebGL2).

Fit with ours:
- Density from terrain layers: `GrassField` takes a density mask (red channel, 0 = no grass), `.with_density_from_fn`, and ground from `GrassGround::Heightmap`, `GrassGround::mesh`, or `.with_ground_from_fn`. No splat input, so we bake an R8 mask per grass type from our LTEX layers, one field per cell block; masks are editable at runtime. A `with_ground_from_fn` sampling our terrain height is likely simplest.
- Wind: built-in wind can be turned off and `GrassWind` driven from our own resource (README `custom_wind` example). A small bridge system maps `sf_wind` to `GrassWind`.
- LOD: GPU near/mid/far plus the far-grass material (the ROADMAP note's "3 LODs"). No custom meshes, so Morrowind groundcover mods (Phase 4 (b)) stay our own work.
- Renderer: deferred/prepass/motion-vector aware, so it should sit with TAA and DLSS; verify against our pinned Bevy and the Solari path (grass is probably not in the RT acceleration structure).
- Budget: 0.3 to 3.4 ms GPU against the 11 ms High target; tie `GrassQuality` to our presets (Low = off or far-only).

Risks: very young, one maintainer, fast API churn (four releases in four days). Pin after the planned crate "update all" pass.

Verdict: adopt later. Time-boxed Phase 4 spike (groundcover (a)): one Seyda Neen cell, mask baked from LTEX, wind bridged, cost measured on the 4060 laptop at High 1440p DLSS Quality. The ROADMAP entry says "git only"; it is now on crates.io (0.20.6), so update it.
