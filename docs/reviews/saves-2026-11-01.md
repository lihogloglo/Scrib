# Cross-review: Saves (2026-11-01)

Scope: the save system end to end. That covers the framework container and file layer (`sf_save`: container, fs, slots, registry), the Bevy runner and sections (`sf_save_bevy`), and the Morrowind adapter and save/load menu (`mw_saves_bevy`), measured against `superfargoth/docs/specs/save.md` and the save decisions (we1 2026-10-18, saves2 2026-10-25). Method: three reviewers worked from different context. The insider read the docs and the code, the outsider read the code only, and the industry reviewer did web research first and then read the code. Each finding then faced an intent refuter and a technical refuter, and outcomes were computed mechanically. This report merges duplicates and changes no outcome. Nothing was built or run, so the perf figures come from the spec and from test comments.

Overall verdict: the core is sound. Atomic temp-file writes, per-section hashes, checks before apply, dormancy for unknown sections and off-thread encode/decode all hold up. The weak spots are the edges of a load: (1) the world is replaced before the fade starts, (2) a failed apply leaves a half-loaded world that autosave can then persist, and (3) a corrupt newest save offers no fallback. Two cheap game-side gaps also cost data in every save written today: `SaveIdentity` is never filled, and `sf/weather` is never registered. The one perf concern, the main-thread snapshot, is already recorded and deferred. It comes back as a challenge to that deferral.

## Confirmed

Ranked by severity.

### C1. Load applies the whole world before the fade starts, and a load that arrives mid-fade loses its travel (high)
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:839-846` (finish_load -> apply); `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:257` (StartTravel{reload:true} written inside the apply); `superfargoth/crates/sf_world_bevy/src/fade.rs:219-224, 242-244`
- **Category:** correctness
- **Claim:** `finish_load` swaps the overlay, RPG, clock and inventory in `Last` on the frame the job ends. The fade-out starts one frame later, and `reload_resident` runs only at the cut. For about 0.3 s (`fade_secs`) the old resident cells keep simulating on top of the loaded state. Non-reload deactivations write the old live state back into the loaded overlay, and pickups land in the loaded RpgState. `run_fade` also drops any StartTravel that arrives when the fade is not Idle, and the load runner never checks SaveGate, so a load arriving during a door fade replaces state but never respawns cells or moves the player.
- **Standard:** save.md "Loading" step 4 and DECISIONS saves2 ("behind the fade"). OpenMW `statemanagerimp.cpp` loadGame runs cleanup() before reading records, so gameplay never ticks in between.
- **Suggestion (reviewer's):** split the load into decode + start fade, then check/reset/apply/reload_resident in one frame at the cut. Queue or gate loads until the fade is Idle.
- **Refuter notes:** both upheld. The technical refuter narrows the mid-fade half: the quickload key (`mw_saves_bevy/src/lib.rs:305`) and the menu (`menu.rs:348`) already refuse a load during a fade. What remains exposed is a door fade that starts during the ~35 ms decode, and callers that don't check (main_menu Continue, scripts). The ordering bug holds on its own.
- **Found by:** insider.

### C2. The game never fills `SaveIdentity`, and the load compares nothing in sf/meta (medium-high, cross-validated)
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:125, 426, 749` (definition, Default init, build_meta read); `superfargoth/crates/sf_save_bevy/src/lib.rs:596-634` (LoadJob::run); `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:261-268`
- **Category:** correctness / industry-gap
- **Claim:** no crate in the workspace writes `SaveIdentity`. Every save written today has an empty content_id, profile and load_order and a zero fingerprint. The load never reads them, so a save from another content pack, mod profile or GRID_CELL applies silently. The S3 mod diff will have nothing to compare these saves against.
- **Standard:** save.md "What is saved" (l.79-81), "Loading" step 2 and "Mod-list changes". OpenMW `StateManager::verifyProfile` (content-file mismatch prompt). Factorio mod sync.
- **Suggestion (reviewer's):** fill SaveIdentity from the resolved profile (`mw_boot_bevy::mods` / `mw_mods`) now. Add a cheap pre-apply check (refuse a content_id or grid_cell mismatch, log a load-order difference) before S3. Add a test that a save carries a non-empty load order.
- **Refuter notes:** all four verdicts upheld. The load-side diff and dialog are S3 (not built). Filling the identity is not deferred anywhere, and it is not in ROADMAP 2.5 "Left".
- **Found by:** insider (I3), industry (X1).

### C3. A failed apply leaves a half-loaded world with no rollback, and autosave can persist it (medium, cross-validated)
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:851-866, 875-899`; `superfargoth/crates/sf_save_bevy/src/sections/mod.rs:166-176`
- **Category:** error-handling
- **Claim:** `apply_with` runs the checks, then the reset hooks, replaces DormantSections, and applies providers in order, returning at the first Err. `apply()` returns at `result?` before SaveSession (world_id, sequence) is updated. The gate stays open, so the next autosave writes the mixed state into the previous world's rotation. The error text itself says "the world may be partly loaded" (lib.rs:395).
- **Standard:** two-phase load (decode and validate, then an infallible commit). OpenMW loadGame catches the failure, runs cleanup(true) and returns to the main menu. Unreal deserializes into a fresh USaveGame before touching the world.
- **Suggestion (reviewer's):** make provider apply infallible by moving the character player-key check (`sections/mod.rs:170-171`) into check. Failing that, block SaveGate on an Apply error and return to the main menu.
- **Refuter notes:** all four upheld. Correction: Check errors happen before any reset, so only Apply errors are affected. Reachability is low today: the only fallible built-in apply is the character key check. `SectionIo::apply` is a public fallible seam, though.
- **Found by:** outsider (O3), industry (X4).

### C4. Overwriting with `.bak` is two renames, and an orphaned `.bak` is never recovered (medium, cross-validated)
- **Where:** `superfargoth/crates/sf_save/src/fs.rs:161-172`; `superfargoth/crates/sf_save/src/slots.rs:216` (test: `.sfsave.bak` parses to None)
- **Category:** error-handling / correctness
- **Claim:** with keep_backup, write_atomic renames the target to `.bak` and then renames the temp file onto the path. A crash between the two leaves no file under the save's name. Listing skips `.bak` and nothing restores it, so an overwritten manual save drops off the load screen. Slot saves use new sequence names, but the menu's overwrite (`SaveTarget::Path`, `menu.rs:17`) takes this path. There is also no retry on a Windows sharing violation (antivirus, OneDrive).
- **Standard:** Win32 ReplaceFileW (one call, keeps a backup; Zed's "windows: Fix atomic write (#30234)"). POSIX: link(target, bak), then rename(tmp, target), so the target name always exists. save.md "Corruption safety" 1 ("old save untouched").
- **Suggestion (reviewer's):** keep the target name populated (hard link or copy to `.bak`, then a single rename, or ReplaceFileW). Surface or restore an orphaned `.bak` in listing. Retry on a sharing violation.
- **Refuter notes:** all four upheld. The window is tiny. `std::fs::rename` already replaces atomically on Windows, so moving the target away first is not needed.
- **Found by:** insider (I5), industry (X2).

### C5. No fallback to an earlier save when the newest is corrupt (medium)
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:602, 608-613`; `superfargoth/crates/sf_save/src/slots.rs:178-180`
- **Category:** industry-gap
- **Claim:** `LoadSource::Latest` picks the newest file whose meta-only read succeeds. A later section hash failure returns an error, and no older candidate is tried and no `.bak` is offered. F9 and Continue simply fail while good rotated saves sit next to the bad one. save.md "Corruption safety" 4 promises this offer, and As built does not list it as missing.
- **Standard:** Elden Ring `.sl2.bak` and Valheim `.old` (cited in save.md). bugnet.io "Fix game save file corruption on power loss".
- **Suggestion (reviewer's):** for Latest, try candidates newest first until one fully verifies. For an explicit path, return the newest earlier verified save of the same world (or the `.bak`) in the error.
- **Refuter notes:** both upheld. Distinct from C3 (corrupt bytes, not apply failures). Not in ROADMAP 2.5 "Left".
- **Found by:** industry.

### C6. `sf/weather` is never registered by the game, so scripted weather overrides are lost on load (medium)
- **Where:** `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:127-157` (register); `bevyrrowind/crates/mw_environment_bevy/src/weather.rs:134, 215-231`; `bevyrrowind/crates/mw_weather/src/script.rs:4, 19`
- **Category:** docs-drift / correctness
- **Claim:** register adds overlay, rpg, clock, characters and mw/rpg only. The game holds a WeatherState with a seed and overrides (ChangeWeather), which DECISIONS we1 makes the saved weather state, so overrides and a non-default seed revert on load. Neither the module's leftovers list nor save.md As built mentions this.
- **Standard:** save.md "What is saved" (l.96) and the S2 deliverable; DECISIONS 2026-10-18 (we1).
- **Suggestion (reviewer's):** register `sections::weather` over the game's resource. Log `sf/records` as a known gap until runtime records exist.
- **Refuter notes:** both upheld. The `sf/records` half is immaterial today (no runtime records in the game).
- **Found by:** insider.

### C7. The blob version table records the build's versions, not the versions the blobs were written at (medium, latent)
- **Where:** `superfargoth/crates/sf_save_bevy/src/sections/mod.rs:139-143`; `superfargoth/crates/sf_save_bevy/src/sections/overlay.rs:44-53`
- **Category:** correctness
- **Claim:** the snapshot stamps the current BlobVersions on the whole overlay. The set path drops `v.blob_versions`, and check only refuses newer versions. After the first `declare()` bump, an older save's unmigrated blobs get re-saved under the new version number, and their real version is lost for good. One table cannot describe blobs of mixed versions.
- **Standard:** per-record versioning (Bethesda change forms carry their own version; OpenMW reads records at the save's format version).
- **Suggestion (reviewer's):** until migration exists, refuse older blob versions or write the loaded table back unchanged. Better: version each blob, or migrate every blob right after decode.
- **Refuter notes:** both upheld as latent. Only tests call `declare()` (`tests.rs:616, 625`). The spec defers migration to overlay v2, but that deferral does not cover re-stamping.
- **Found by:** insider.

### C8. An autosave refused by `can_save` is dropped until the next full interval (medium, latent)
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:439-447, 692-701`
- **Category:** correctness
- **Claim:** `tick_play_time` resets `elapsed` when it emits Auto. A `can_save` refusal becomes `SaveDone(Err(Refused))` with no retry. Only gate blockers keep a request waiting, and `can_save` is meant for exactly the conditions that persist (enemies nearby), so a player in combat zones can go 20+ minutes without an autosave.
- **Standard:** deferred autosave (Bethesda games and The Witcher 3 postpone a pending autosave until it is safe).
- **Suggestion (reviewer's):** treat an Auto refusal as pending and re-check periodically, or leave `elapsed` at the interval.
- **Refuter notes:** both upheld. Latent: no game code sets `can_save` yet (only `tests.rs:469`). The rule itself is save.md open question 3.
- **Found by:** outsider.

### C9. The read-back check compares against the page cache and does not do the hash pass the spec promises (low)
- **Where:** `superfargoth/crates/sf_save/src/fs.rs:156-160`; spec `superfargoth/docs/specs/save.md:204-205, 328`
- **Category:** correctness / spec honesty
- **Claim:** after `write_synced`, the temp file is read back with a plain buffered `fs::read` and byte-compared. The OS cache almost certainly serves that read, so it catches nothing beyond a misbehaving SaveFs. save.md "Corruption safety" 2 promises a read-back of "preamble, TOC, every hash" before rotation, and the code never parses or hashes the bytes.
- **Standard:** Dan Luu, "Files are hard"; fsync(2): durability rests on fsync ordering, not read-back.
- **Suggestion (reviewer's):** run a real `SaveFile::open` structure and hash check, or drop the step and document that the load-time blake3 is the guard. Either way, state the step's real purpose.
- **Refuter notes:** both upheld. The cost is immaterial (off-thread). Related to refuted O5, which argued the read-back should go for perf reasons. The refuters kept the step as a deliberate spec rule; X9 survives because the code is weaker than the spec says.
- **Found by:** industry.

### C10. `mw_saves_bevy` module docs describe behaviour the code no longer has (low)
- **Where:** `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:11, 26, 32-33` vs `:169, 227, 251-257`
- **Category:** docs-drift
- **Claim:** the docs say the body is not saved (`body: None`), that removed placements go through `inventory::take_placement` (the name appears nowhere else in the crate), and that taken items reappear only on cell reload. The code saves and restores the body, and the load does a full resident reload (`StartTravel{reload:true}`). The "Not yet" list also still names the body's motion state.
- **Suggestion (reviewer's):** rewrite the Sections, Quickload and Not yet bullets to match the 2026-10-25 load path.
- **Refuter notes:** both upheld.
- **Found by:** insider.

## Challenges to recorded decisions

### CH1. Main-thread save snapshot over budget; the copy-on-write fix waits on an untracked condition (cross-validated)
- **Where:** `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:162-166` (overlay deep clone under the RwLock); `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:109-114, 131` (RpgState clones); `superfargoth/crates/sf_save_bevy/src/lib.rs:692-723` (serial snapshots in the exclusive `drive`); `superfargoth/crates/sf_save_bevy/src/tests_budget.rs:222-224`
- **The decision:** save.md "As built (S1, S2)", Budgets (l.351-354). The snapshot measures 3.5-5.6 ms warm and ~9 ms cold against a 5 ms budget, dominated by the overlay copy. "If the owner's laptop confirms: copy-on-write overlay in sf_world (persistent maps or Arc'd per-cell buckets)."
- **The argument against:** the project's own measurement already breaks the 5 ms budget by up to ~2x (~9 ms cold against an 11 ms frame). The cost grows without bound as the overlay grows, and the RpgState clones come on top unmeasured. Autosave is on by default every 10 minutes, so the hitch lands in exactly the long sessions it targets. The fix is the one the spec already names, the "laptop confirms" condition has no ROADMAP line, and the budget test prints but does not assert. Standards cited: `im`/`rpds` persistent maps, Bethesda per-form change deltas, Factorio non-blocking save, Naughty Dog GDC 2015.
- **What the refuters said:** O1's intent refuter raised it as a challenge and its technical refuter upheld it, rating it medium rather than high. I2 and X6 were refuted by both refuters on the same facts: the cost is a single-frame spike every 10 minutes on a synthetic 100-hour world measured on cloud hardware, it does not move the median frame target, and deferral follows "diagnose before optimizing" and "log, don't chase". Everyone agrees the ROADMAP line is missing.
- **Owner decides:** keep the deferral (and add a ROADMAP line with the measurement), or schedule the COW overlay now.
- **Found by:** insider (I2), outsider (O1), industry (X6).

## Disputed

### D1. Save list, Continue and fresh-run F9 scan every save file on the main thread (cross-validated)
- **Where:** `bevyrrowind/crates/mw_saves_bevy/src/menu.rs:104-122, 381-397`; `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:314, 326-334` (newest_save); `superfargoth/crates/sf_save/src/slots.rs:159-185`
- **Claim:** Folder::list, refill or relist on every SaveDone while the screen is open, and newest_save all open each file and run read_meta synchronously inside Update systems. Manual saves never rotate, so the cost grows without bound. Hundreds of files on Windows (Defender, cloud-synced Documents) make a visible stall. `latest()` lists everything to find one file.
- **Upholding (all three technical refuters):** the code path is real and unbounded, and per-file open costs add up on Windows. The well-known Skyrim slow save menu is the same pattern. Cheap partial fix: have latest() sort by the file-name sequence.
- **Refuting (all three intent refuters):** the format makes sf/meta first and Raw so a list read is "a few KiB" (save.md:67). Every call site is a paused menu or the start of a load behind a fade, never a gameplay frame. Nothing measured shows a stall. OpenMW's CharacterManager also reads headers synchronously. Thumbnails do not exist yet.
- **Found by:** insider (I9), outsider (O6), industry (X10).

### D2. Runtime record patches form an op log that grows with play time
- **Where:** `superfargoth/crates/sf_save_bevy/src/sections/records.rs:169-175, 183-197` (the finding cited l.349, which doesn't exist)
- **Claim:** `RecordOverlay::patch` merges only with the immediately previous entry for the same record and never collapses repeated Sets, and load replays every op. Save size and load time grow with play time rather than with state. Bethesda change forms and OpenMW store current deltas.
- **Upholding (technical):** the behaviour is real and nothing compacts the log, so it is a genuine design flaw once the overlay is used. Severity is medium/latent.
- **Refuting (intent):** nothing in production produces patches (callers only in `tests.rs:731-733`), the game wires no sf/records section, and save.md:344-345 marks RecordOverlay as interim until sf_records has a runtime overlay. Compaction is a design question for that future overlay.
- **Found by:** outsider.

### D3. CPU-heavy encode/decode run on IoTaskPool
- **Where:** `superfargoth/crates/sf_save_bevy/src/lib.rs:473-480`
- **Claim:** the whole save job (postcard, LZ4, blake3, read-back) and load job run on IoTaskPool, which bevy_tasks documents as IO-bound and which bevy_asset shares, so they contend during streaming.
- **Upholding (intent):** the choice contradicts the bevy_tasks docs, and no comment or decision justifies it. Low severity.
- **Refuting (technical):** the job is ~30 ms once per autosave. Bevy's own asset server runs CPU-heavy loader futures on IoTaskPool (`bevy_asset-0.20 src/server/mod.rs:427, 494`). Moving it would change no measured outcome.
- **Found by:** industry.

### D4. No quit handling: no exit save, and a save in flight can be lost on exit
- **Where:** `bevyrrowind/crates/mw_saves_bevy/src/lib.rs:261-268`; `superfargoth/crates/sf_save/src/slots.rs:183-185`; `superfargoth/crates/sf_save/src/fs.rs:151-156`
- **Claim:** `SaveReason::Exit` and its rotation exist, but nothing reacts to AppExit. No exit save is requested, quitting does not wait for a running save job, and stale `.tmp` files pile up.
- **Upholding (intent):** confirmed, no AppExit handling anywhere. Low severity because atomicity keeps the old file.
- **Refuting (technical):** save.md lists Exit only as a reason with a rotation count and has no save-on-quit requirement, so this is an unspecified feature. The loss window is ~30 ms. The stale-`.tmp` claim is wrong: the next save reuses the failed sequence and overwrites the same `.tmp`.
- **Found by:** industry.

## Refuted

- **I7** sf_save_bevy is a hub owning every system's schema: a deliberate As built choice ("owners stay save-agnostic; shape goldens fail here"), and As built wins under the spec's precedence rule. At most the Versioning paragraph is stale.
- **I8** Autosave has no can_save rule and no streaming-burst blocker: in-play bursts start only behind the fade gate, and the combat rule is open question 3.
- **O4** The load hashes and decompresses each section twice: real but immaterial (off-thread, ~35 ms against a 300 ms budget). Up-front verify is spec load step 1.
- **O5** finish clones payloads, and the read-back doubles the I/O: the clone is immaterial (off-thread, ~30 ms against 500 ms), and the read-back is a spec rule (see C9 for the part that survived).
- **O7** next_sequence and rotation re-read every meta: off-thread, head-only, and the second listing happens only for auto/quick groups.
- **O9** Spawned actors' inventories are dropped by the key-range heuristic: runtime spawns already get persistent 128-bit ids from a saved counter. Only placement-less characters use entity bits, which cannot be saved anyway.
- **O10** A superseded load gets no LoadDone, and quickload reports false success: LoadDone has no request id, so nothing can hang. The empty worldspace is a deliberate sentinel, and the game always has a camera.
- **X3** Windows writes count as durable, so rotation deletes too early: the NTFS log replays in order, so a delete cannot persist while the rename is lost. The data was already sync_all'd, and the spec says the directory fsync is POSIX-only.

- **Fixed:** C1-C10, plus a pre-existing break the review missed (combat C1a / lock-on changed the saved
  `sf.character` shape without a version bump; now `sf.character.v2` with a v1 migration, the S2 golden loads).

- **Leftovers:** the game should return to the main menu on `LoadError::partly_loaded()` and offer
