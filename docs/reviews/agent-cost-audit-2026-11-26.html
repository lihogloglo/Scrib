Agent cost audit

Scrib, Thursday 2026-11-26. Meta-coordinator workflow against the previous orchestrator workflow. Written 22:40.

The spend went to the orchestration layers, not to the messages and not to the tasks. In the meta workflow, the sessions that plan, brief, verify, commit and report cost as much as the sub-agents that write the code, and about twice as much once those sessions ran on Fable (from about 16:30). In last night's workflow the same layer cost 30 % on top of the workers.

The messages between sessions are a small part: the meta-coordinator is about 6-8 % of the day. The 250k line is neither the cause nor a saving.

Today cost roughly $1,000-1,400 at API prices in this project, against $2,302 for the previous 14 days together ($177 per active day). So about half of the previous two weeks in one day. Six sessions (meta-8 and five lanes) were still running when this was written.

3. Is it the talking?

No. The meta-coordinator cost $8.1 in its first 80 minutes (24 messages in, 36 out), and eight meta sessions come to about $65-95, 6-8 % of the day. In a lane session, messages with meta add 10-15k tokens of context out of about 175k.

What costs is that each layer is a full agent that carries and re-reads a large context on every call. Three layers (meta, lane, sub-agent) means three contexts paid for each slice.

4. Is it the 250k line?

No, in both directions. Carrying 150k of extra context costs $0.03 per call (cache reads are $0.20 per million tokens on Opus and Fable). Starting a fresh session costs about $1-1.6 (writing 61k of fixed context plus the read-in). The two roughly cancel over a normal session. No measured session lost its cache (0 cold re-writes), so waiting on the build queue cost time, not tokens.

The lever is how many slices a session finishes before it reaches the line: 16-23 last night, 3 today. Last night's sessions ran to 312k and 377k and were the cheapest per slice of the day.

6. What could not be measured

  • Sessions launched by meta keep no transcript. 60 of the 66 session folders created today have sub-agent records but no .jsonl; the first one starts at 12:25, when meta began launching sessions itself. tools/session_context.sh reads those transcripts, so it has shown no lane since 14:50. The likely cause is the environment a session passes to the ones it starts (CLAUDE_CODE_CHILD_SESSION); this was not confirmed.
  • meta-8 could not be asked: it is not in this session's peer list, and it holds no token data anyway.
  • The plan's own meter. /usage in any session shows the real percentage used; the dollar figures here are a proxy for it.

7. Recommendations, largest saving first

  1. Go back to two layers. Two or three lane orchestrators that you talk to directly, each running many sub-agents per session, as last night: 30 % overhead instead of 95-200 %. The build queue already limits useful parallel work to about four lanes. If one window matters more than cost, keep meta but accept its price.
  2. Run orchestrators on Opus. Remove "model": "fable" from the user settings or pass --model opus in the launch command. Keep Fable for the session you talk to.
  3. Cut bigger slices. A feature such as swing doors as 3-4 sub-agents, not 16. Sub-agents peak at a median of 119-142k, well under the 250k line, so a slice can be about twice as large.
  4. Batch the ceremony. One commit, push and docs pass (roadmap, changelog, ledger, wiki) per batch of slices, not per slice. This is where the extra orchestrator calls went.
  5. Queue what ends on screen. A third of today's agents wrote specs or research, and most code landed in cores and tests. To feel progress, the queue needs slices that finish with game wiring and a scene to check.
  6. Fix the transcript gap before running the meta workflow again, so its cost can be seen while it runs.
